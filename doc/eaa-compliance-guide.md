## 1. 法案概述

### 1.1 基本信息

| 项目 | 内容 |
|------|------|
| **正式名称** | 欧盟无障碍法案（European Accessibility Act） |
| **指令编号** | (EU) 2019/882 |
| **通过日期** | 2019年4月17日 |
| **发布日期** | 2019年6月7日 |
| **强制实施日期** | **2025年6月28日** |
| **核心目标** | 确保残障人士平等访问产品和服务，促进无障碍产品和服务在欧盟范围内自由流通 |

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **通用性** | 产品功能应能通过多种方式（如键盘、语音、触觉）操作，避免仅依赖单一交互模式 |
| **非歧视性** | 无障碍功能需作为产品默认配置，而非需额外付费或激活的附加功能 |
| **可适应性** | 支持用户自定义设置（如字体大小、对比度、语音反馈强度），以满足不同残障需求 |

### 1.3 处罚措施

| 国家 | 罚款金额 | 其他措施 |
|------|---------|---------|
| **德国** | 最高50万欧元 | 服务暂停 |
| **法国** | 5,000 - 25万欧元 | 公开曝光违规公司 |
| **西班牙** | 5,000 - 30万欧元 | 强制纠正措施 |
| **爱尔兰** | 最高可判入狱 | - |
| **意大利** | 最高10万欧元 | - |

## 2. 适用范围

### 2.1 产品类

| 类别 | 具体产品 |
|------|---------|
| **消费类计算机硬件及操作系统** | 台式机、笔记本电脑、操作系统 |
| **自助终端设备** | POS机、ATM机、售票机、自助值机终端、信息交互式终端（非交通工具集成部件） |
| **电子通信终端设备** | 智能手机、平板电脑、路由器、光猫等具有交互式计算能力的设备及辅助设备 |
| **视听媒体服务终端** | 电视设备、机顶盒、电子阅读器 |

### 2.2 服务类

| 类别 | 具体服务 |
|------|---------|
| **电子通信服务** | 紧急呼叫服务（如"112"）、语音通信、视频通话等（不含机器对机器传输服务） |
| **视听媒体服务访问** | 网站、移动应用程序、电子票务服务、实时旅行信息服务 |
| **客运服务** | 航空、铁路、公路、水上客运的网站、移动应用、电子票务系统（不含城市/郊区/区域运输） |
| **个人银行服务** | 网上银行、移动银行应用 |
| **电子书及专用软件** | 电子书平台、专用软件服务 |
| **电子商务服务** | 官方网上商城、在线支付系统 |

### 2.3 豁免范围

| 豁免类型 | 说明 |
|---------|------|
| **微型企业** | 员工人数少于10人、收入低于200万欧元的企业 |
| **历史内容** | 2025年6月28日前发布的预先录制视频、Office文件格式 |
| **第三方内容** | 非经济运营商开发或资助的内容 |
| **存档内容** | 2025年6月28日后未更新的静态内容 |
| **特殊服务** | 公共广播机构网站、非政府组织网站（不提供公共服务） |
| **紧急服务** | 紧急通信服务（如"112"）的无障碍要求可延迟至2027年6月28日 |

### 2.4 过渡期安排

| 场景 | 执行要求 |
|------|---------|
| **2025年6月28日后新投放的产品/服务** | 必须立即符合无障碍标准 |
| **2025年6月28日前已签订合同的服务** | 可在合同期内继续使用，最长过渡期至**2030年6月28日**（不超过5年） |
| **2025年6月28日前投入使用的自助终端** | 可继续使用至使用寿命结束，但最长不超过**投入使用后20年** |

## 3. 合规标准

### 3.1 核心标准

| 标准 | 版本 | 地位 |
|------|------|------|
| **WCAG** | 2.1 Level AA | 网站和移动应用的核心技术标准 |
| **EN 301 549** | V3.2.1 / V4.1.1 | EAA的推荐性参考标准，涵盖ICT产品和服务 |

### 3.2 EN 301 549 核心模块

| 模块 | 内容 |
|------|------|
| **通用性要求** | 封闭功能需提供非视觉访问方式；生物识别不应作为唯一身份验证方式；按键重复、切换控件需支持非视觉识别 |
| **功能性要求** | 针对全盲、视力受限、色盲、听觉受限、语音能力受限等不同障碍类型提供定制化功能 |
| **软硬件兼容性** | 支持USB、蓝牙等标准连接；内置软件和网页浏览器需与WCAG 2.1 AA兼容 |
| **用户界面设计** | 支持放大、对比度调整、非色彩编码等无障碍特性 |

## 4. 网站与移动应用合规要点

### 4.1 可感知性 (Perceivable)

#### 4.1.1 非文本内容的替代

| 要点 | 说明 | 代码示例 |
|------|------|---------|
| **图片必须有 alt 属性** | `<img>` 标签必须包含描述性的 `alt` 文本 | `<img src="logo.png" alt="公司Logo">` |
| **装饰性图片** | 使用装饰性图片时需设置空 `alt=""` | `<img src="bg-pattern.png" alt="">` |
| **复杂图像** | 图表、图形需提供完整的文字描述或链接到详细描述页面 | 使用 `aria-describedby` 关联详细描述 |
| **音频视频** | 所有视频必须提供同步字幕，音频需提供文本转录 | 使用 `<track>` 标签添加字幕 |

#### 4.1.2 文字可读性

| 要点 | 说明 | 合规阈值 |
|------|------|---------|
| **对比度达标** | 文本与背景对比度需达标 | 普通文本 ≥ 4.5:1，大文本 ≥ 3:1 |
| **支持缩放** | 页面在 200% 缩放时仍可正常使用 | 不使用固定像素单位（如 px）定义布局 |
| **无闪烁内容** | 避免 2-55Hz 频率的闪烁 | 使用 `prefers-reduced-motion` 媒体查询 |

#### 4.1.3 颜色使用

| 要点 | 说明 | 常见问题 |
|------|------|---------|
| **颜色不能作为唯一识别方式** | 表单验证、状态指示等需配合图标或文字 | ❌ 仅用红色表示错误，绿色表示成功 |
| **支持颜色反转** | 用户系统开启颜色反转时仍可正常使用 | ❌ 硬编码颜色值导致反转后不可读 |

### 4.2 可操作性 (Operable)

#### 4.2.1 键盘访问

| 要点 | 说明 | 测试方法 |
|------|------|---------|
| **所有功能可通过键盘访问** | 无需鼠标即可完成所有操作 | 全程使用 Tab/Enter/Arrow 键操作 |
| **无键盘陷阱** | Tab 键可在所有可聚焦元素间正常循环 | 在所有可交互区域测试 Tab 键循环 |
| **焦点可见** | 当前聚焦元素有清晰的视觉指示 | 检查是否有焦点样式（outline 或自定义样式） |

#### 4.2.2 焦点管理

| 要点 | 说明 | 测试方法 |
|------|------|---------|
| **焦点顺序合理** | Tab 键顺序符合视觉布局和逻辑流程 | 按 Tab 键检查焦点移动顺序 |
| **Modal 焦点陷阱** | 打开弹窗时焦点进入，关闭时焦点返回原触发元素 | 打开/关闭弹窗测试焦点行为 |
| **提供跳过链接** | 页面顶部提供"跳转到主内容"链接 | 检查页面顶部是否有 skip link |

#### 4.2.3 时间限制

| 要点 | 说明 | 实现方式 |
|------|------|---------|
| **提供时间延长选项** | 限时操作（如验证码）需允许用户延长时间 | 提供"重新发送"按钮或延长倒计时选项 |
| **无时间限制的操作** | 重要操作不应设置强制时限 | 表单填写、文件上传等不应有强制超时 |

### 4.3 可理解性 (Understandable)

#### 4.3.1 语言与语义

| 要点 | 说明 | 代码示例 |
|------|------|---------|
| **页面语言明确** | `<html>` 标签需设置 `lang` 属性 | `<html lang="zh-CN">` |
| **语义化 HTML** | 使用语义标签而非纯 `<div>/<span>` | `<header>`, `<nav>`, `<main>`, `<footer>` |
| **ARIA 属性正确使用** | 自定义组件需添加适当的 ARIA role 和属性 | `role="button"`, `aria-label`, `aria-expanded` |

#### 4.3.2 输入与验证

| 要点 | 说明 | 代码示例 |
|------|------|---------|
| **表单标签关联** | 每个表单字段必须有对应的 `<label>` | `<label for="email">邮箱</label><input id="email">` |
| **错误提示清晰** | 错误消息明确指出问题和修复方法 | "请输入有效的邮箱地址，如 example@email.com" |
| **错误消息可访问** | 使用 `aria-describedby` 关联错误消息 | `<input aria-describedby="email-error">` |

#### 4.3.3 一致性

| 要点 | 说明 | 检查项 |
|------|------|---------|
| **导航一致** | 导航元素在所有页面位置和样式保持一致 | 检查各页面导航布局是否相同 |
| **操作一致** | 相似功能使用相同的交互方式 | 检查相同操作在不同页面的行为是否一致 |

### 4.4 健壮性 (Robust)

#### 4.4.1 代码质量

| 要点 | 说明 | 检查方法 |
|------|------|---------|
| **有效 HTML/CSS** | 代码符合 W3C 规范，无语法错误 | 使用 W3C 验证器检查 |
| **兼容辅助技术** | 支持主流屏幕阅读器（JAWS、NVDA、VoiceOver） | 使用屏幕阅读器测试 |
| **状态消息可访问** | 使用 `aria-live` 区域播报状态变化 | `<div aria-live="polite">操作成功</div>` |

#### 4.4.2 兼容性

| 要点 | 说明 | 测试范围 |
|------|------|---------|
| **支持多种浏览器** | 兼容主流浏览器的最新版本及前一个版本 | Chrome、Firefox、Safari、Edge |
| **支持多种设备** | 桌面端、移动端、平板端均需兼容 | 测试不同屏幕尺寸 |

### 4.5 移动应用特有要求

| 要点 | 说明 | 实现方式 |
|------|------|---------|
| **触摸目标大小** | 可点击元素最小 44×44pt | 设置 `minWidth`/`minHeight` ≥ 44pt |
| **语音控制支持** | 支持 Siri/Google Assistant 语音操作 | 添加语音控制指令 |
| **屏幕阅读器兼容** | 支持 VoiceOver（iOS）和 TalkBack（Android） | 设置 `accessibilityLabel` |
| **无障碍标签** | 为自定义组件提供标签 | 使用 `accessibilityLabel`/`contentDescription` |
| **键盘导航** | 支持外接键盘操作 | 确保所有交互元素可通过键盘访问 |

## 5. 合规路径与流程

### 5.1 四阶段合规模型

```
阶段一：技术合规（WCAG 2.1 AA）
├── 自动化检测（axe-core, WAVE）
├── 人工测试（键盘操作、屏幕阅读器）
├── 用户测试（邀请残障用户）
└── 修复所有严重违规

阶段二：文档与声明
├── 编写技术文件
├── 发布无障碍声明页面
├── 制定欧盟符合性声明
└── 加贴 CE 标签（如适用）

阶段三：服务支持
├── 提供无障碍客服渠道
├── 培训客服人员
└── 提供无障碍格式文档

阶段四：持续维护
├── 定期合规评估（至少每五年一次）
├── 开发流程中集成无障碍检查
└── 监控用户反馈并持续改进
```

### 5.2 合规评估流程

| 步骤 | 内容 | 责任人 |
|------|------|--------|
| 1 | 确定产品/服务是否在 EAA 适用范围内 | 法务/合规负责人 |
| 2 | 评估是否属于豁免范围（微型企业等） | 法务/合规负责人 |
| 3 | 进行无障碍测试（自动化 + 人工） | 开发/测试团队 |
| 4 | 修复发现的无障碍问题 | 开发团队 |
| 5 | 准备技术文件和合规声明 | 技术负责人 |
| 6 | 发布无障碍声明页面 | 产品/营销团队 |
| 7 | 建立持续监控和改进机制 | 合规负责人 |

## 8. 常见合规陷阱

### 8.1 技术陷阱

| 陷阱 | 后果 | 避免方法 |
|------|------|---------|
| **仅靠自动化工具检测** | 漏检行为级问题（键盘陷阱、焦点管理） | 结合人工测试和用户测试 |
| **忽略第三方组件** | 第三方库（日历、地图、支付）不合规 | 审查所有依赖组件的无障碍性 |
| **无测试计划** | 开发后期发现大量问题难以修复 | 建立无障碍测试流程，在开发早期介入 |
| **使用纯CSS自定义按钮** | 按钮无法通过键盘访问 | 使用原生 `<button>` 或添加 `role="button"` 和 `tabindex` |
| **使用placeholder代替label** | 屏幕阅读器无法正确读取表单 | 始终使用 `<label>` 元素 |

### 8.2 流程陷阱

| 陷阱 | 后果 | 避免方法 |
|------|------|---------|
| **无合规声明** | 无法证明已完成合规工作 | 发布无障碍声明页面，记录合规过程 |
| **无技术文件** | 监管机构检查时无法提供证明 | 提前准备技术文件 |
| **不进行定期评估** | 违反"至少每五年评估一次"的要求 | 建立定期评估机制 |
| **忽略服务支持要求** | 技术合规但服务不合规 | 同时准备技术和服务支持 |

### 8.3 认知陷阱

| 陷阱 | 实际情况 | 正确做法 |
|------|---------|---------|
| **"我们的用户没有残障人士"** | 欧盟约1.3亿人有某种形式的残疾 | 设计面向所有用户的产品 |
| **"无障碍太昂贵"** | 早期介入成本更低，后期修复成本高 | 在设计阶段考虑无障碍 |
| **"自动化工具通过就够了"** | 自动化工具只能检测约30%的问题 | 必须进行人工测试 |
| **"我们是小公司，可以豁免"** | 只有员工<10人且收入<200万欧元才能豁免 | 核实公司规模是否符合豁免条件 |

## 9. 自查清单

### 9.1 快速自查清单

```
□ 所有图片有 alt 属性
□ 文本对比度 ≥ 4.5:1
□ 所有功能可通过键盘访问
□ 无键盘陷阱
□ 焦点可见且顺序合理
□ 表单有正确的 label 关联
□ 语义化 HTML 结构
□ ARIA 属性正确使用
□ 支持屏幕阅读器
□ 响应式设计适配多设备
□ 提供跳过链接
□ 颜色不能作为唯一识别方式
□ Modal 焦点管理正确
□ 错误消息清晰且可访问
□ 页面语言明确设置
```

### 9.2 详细自查清单

#### 可感知性

```
□ 所有 <img> 标签有 alt 属性
□ 装饰性图片使用空 alt=""
□ 复杂图像有详细文字描述
□ 视频有同步字幕
□ 音频有文本转录
□ 文本与背景对比度 ≥ 4.5:1（普通文本）
□ 大文本对比度 ≥ 3:1
□ 页面支持 200% 缩放
□ 无 2-55Hz 频率的闪烁内容
□ 颜色不是唯一的识别方式
□ 支持系统颜色反转设置
```

#### 可操作性

```
□ 所有功能可通过键盘访问
□ 无键盘陷阱（Tab可正常循环）
□ 焦点样式可见
□ Tab顺序符合视觉布局
□ Modal打开时焦点进入
□ Modal关闭时焦点返回原触发元素
□ 提供"跳转到主内容"链接
□ 限时操作提供延长时间选项
□ 无强制超时的重要操作
□ 鼠标悬停内容可通过键盘触发
```

#### 可理解性

```
□ <html> 标签设置了 lang 属性
□ 使用语义化 HTML 标签
□ ARIA 属性正确使用，不过度使用
□ 每个表单字段有对应的 <label>
□ 错误消息清晰说明问题和修复方法
□ 错误消息与对应字段关联（aria-describedby）
□ 导航在所有页面保持一致
□ 相似功能使用相同的交互方式
□ 页面标题清晰描述页面内容
□ 链接文本有明确的目的描述
```

#### 健壮性

```
□ HTML 代码符合 W3C 规范
□ 支持主流屏幕阅读器（JAWS、NVDA、VoiceOver）
□ 动态内容更新时使用 aria-live 区域
□ 兼容主流浏览器（Chrome、Firefox、Safari、Edge）
□ 兼容多种设备（桌面、移动、平板）
□ 无重复的 ID
□ 无未闭合的标签
□ 表单提交有明确的成功/失败反馈
□ 状态变化可被屏幕阅读器读取
□ 错误状态使用 aria-invalid 属性
```

#### 移动应用特有

```
□ 触摸目标大小 ≥ 44×44pt
□ 支持 VoiceOver/TalkBack
□ 自定义组件有 accessibilityLabel
□ 支持外接键盘操作
□ 手势操作有替代方式
□ 屏幕旋转时布局正常
□ 状态栏内容可见
□ 通知可被屏幕阅读器读取
□ 支持系统字体大小设置
□ 支持系统对比度设置
```

#### 文档与声明

```
□ 已发布无障碍声明页面
□ 已准备欧盟符合性声明
□ 已准备技术文件
□ 已提供无障碍客服渠道
□ 客服人员已接受无障碍培训
□ 已提供无障碍格式文档
□ 已建立定期合规评估机制
□ 已记录合规评估过程
□ 已审查第三方组件的无障碍性
□ 已建立用户反馈处理机制
```
